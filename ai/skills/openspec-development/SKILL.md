# Разработка по OpenSpec

OpenSpec управляет требованиями и рабочими пунктами, а Git — реализацией.
Оперативное состояние лишь связывает эти источники и не заменяет их.

## Активация и выбор изменения

Активируй навык только в двух случаях:

* пользователь явно просит применить OpenSpec
* пользователь просит продолжить, реализовать или проверить конкретное активное изменение

Навык не активирует простое упоминание имени изменения. Обычная задача без явного запроса не включает OpenSpec.
Навык не включается только из-за наличия каталога `openspec/`, сложности задачи
или других активных изменений.

Найди CLI через `command -v openspec`, затем через
`./node_modules/.bin/openspec`. Не устанавливай OpenSpec и не запускай команду,
способную скачать пакет. Передай найденный CLI исполняемому интерфейсу ниже.
Он получает полный JSON `openspec list --json` и выбирает ровно одну ветвь:

* **0 активных изменений** — при явном запросе создай новое изменение штатным CLI;
  без явного запроса заверши навык
* **1 активное изменение** — продолжи единственное активное изменение либо
  проверь, что явно названо именно оно
* **N активных изменений** — пользователь выбирает одно; не выбирай по
  недавности, имени или текущей ветке

## Источники истины и восстановление

Приоритет источников: артефакты и полные JSON-ответы OpenSpec, Git, отчёты
ролей, затем `state.md`. Файл `state.md` — восстанавливаемый кеш.
Подготовь безопасную рабочую область через
[scripts/openspec-workspace](scripts/openspec-workspace).

## Исполняемые решения

Все детерминированные ветви и переходы выполняй только через
[scripts/openspec-orchestrate](scripts/openspec-orchestrate):

```bash
scripts/openspec-orchestrate SNAPSHOT_JSON STATE_FILE [OPENSPEC_CLI]
```

Запиши минимальный локальный снимок события и следуй JSON-решению скрипта.
События интерфейса: `discover`, `recover`, `route`, `review`,
`review-complete`, `findings`, `verify`, `archive-guard` и `archive-impact`.
Скрипт атомарно обновляет известные поля `state.md`, но не запускает агентов.
Наблюдаемые действия ролей выполняет этот навык через сохранённые ID.

При новом чате или уплотнении контекста прочитай полные JSON
`openspec list --json`, `openspec status <id> --json` и
`openspec instructions apply <id> --json`, затем Git, отчёты и `state.md`.
Исправь кеш по фактам и запиши причину расхождения.

В `state.md` сохраняй ID планировщика, постоянного исполнителя и проверяющего,
пути отчётов, режим и `verified-head`. Продолжай доступную роль через
`followup_task` и передавай только дельту нового входа. Не пересылай историю
чата, прежние требования или уже прочитанные отчёты.

Если ID недоступен, запиши причину замены, пересчитай `fresh-agent budget` и
создай одну замену с `fork_turns: "none"`. Новый агент должен восстановиться:
восстанови из файлов артефакты, последний отчёт, открытые замечания,
`{STATE_FILE}` и `{REPORT_FILE}`. Потеря ID не повторяет завершённый этап.

## Стадии

`discover` → `planning` → `human-approval` → `execution` → `review` →
`fresh-verification` → `ready-for-merge`.

Переход из `planning` требует явного утверждения артефактов пользователем.
Неполные рабочие пункты блокируют `review`. Архивация не входит в эту машину
состояний.

## Планирование и исполнение

Передай тому же планировщику [planner-prompt.md](planner-prompt.md), имя
изменения, `{STATE_FILE}` и `{REPORT_FILE}`. После утверждения прочитай свежий
`openspec instructions apply <id> --json` и сгруппируй пункты по связанности.

Один связный рабочий блок может содержать несколько ID рабочих пунктов. Создай
для каждого пункта краткий файл через
[scripts/openspec-task-brief](scripts/openspec-task-brief), затем передай
`{TASK_IDS}` и готовые файлы кратких заданий в `[BRIEF_FILES]`. Весь связный
блок получает один постоянный исполнитель и один отчёт через
[implementer-prompt.md](implementer-prompt.md).

Если после группировки остаются два и более независимо принимаемых блока,
выбери режим `sdd`. Передай SDD готовые `[BRIEF_FILES]`, требования OpenSpec,
пути отчётов и `[CALLER_CONTROLLED_RETURN]`; SDD не разбирает JSON OpenSpec.
Один связный блок использует режим `single`.

Каждый новый агент получает `fork_turns: "none"`; модель выбирай по роли и
риску, но не закрепляй её в навыке. Ответ роли — не более 15 строк, подробности
роль пишет в указанный отчёт.

## Ровно одно итоговое ревью

В режиме `single` проведи ровно одно итоговое ревью через
[reviewer-prompt.md](reviewer-prompt.md). Передай все требования, отчёты,
ограниченный пакет и точный диапазон `BASE..HEAD`.

В режиме `sdd` итоговый проверяющий SDD одновременно получает требования OpenSpec и контекст,
проверяет соответствие OpenSpec и является единственным полным проверяющим. Вызывающий навык
получает итоговый отчёт и не запускает второго проверяющего
или второе полное ревью.

Категории замечаний: `artifact {id}`, `implementation`, `external`. Уровни
`Critical` и `Important` блокируют завершение; решение по `Minor` запиши в
`state.md`.

## Смешанные замечания

Если есть замечания `artifact {id}`, выполни один цикл в этом порядке:

1. Сохрани все замечания в отчёте и верни процесс в `planning`
2. Продолжи того же планировщика; исправь только затронутые артефакты
3. Вычисли затронутые выполненные пункты и сними `done` только с затронутых
4. Передай одному постоянному исполнителю обновлённые артефакты и все замечания к реализации
   одним пакетом
5. Продолжи того же проверяющего через
   [re-review-prompt.md](re-review-prompt.md) только с открытыми замечаниями и
   пакетом исправлений

В этой схеме только проверяющий присваивает `OBSOLETE`; планировщик и исполнитель не закрывают
замечание как устаревшее. Внешний блокер задай пользователю одним вопросом и
верни ответ прежней роли.

## Свежая верификация и возврат SDD

После чистого итогового ревью режим `sdd` сохраняет рабочую область и отчёты и
возвращает управление этому навыку. Не очищай SDD и не завершай ветку.

Перейди в `fresh-verification`, получи фактический текущий `HEAD` и сам запусти
свежие проектные проверки. Сравни фактический `HEAD` с проверенным диапазоном и
отчётами. Несовпадение делает доказательства устаревшими. Только успешная
проверка текущего `HEAD` записывает `verified-head: <HEAD>` и переводит процесс
в `ready-for-merge`.

После `ready-for-merge` можно явно разрешить SDD очистить его рабочую область и
перейти к завершению ветки. До этого не запускай второе полное ревью, очистку
или `finishing-a-development-branch`.

## Краткая проверка

| Условие                       | Решение                               |
| ----------------------------- | ------------------------------------- |
| Нет точного условия активации | Не применять OpenSpec                 |
| CLI недоступен                | Сообщить внешний блокер               |
| Один связный блок             | `single`, один постоянный исполнитель |
| Два и более независимых блока | `sdd`, возврат вызывающему навыку     |
| Изменились артефакты          | `planning`, только затронутые пункты  |
| Проверен не текущий `HEAD`    | Повторить свежую верификацию          |
