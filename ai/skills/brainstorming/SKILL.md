# Проработка решений

Помогает превратить неясную идею в согласованное решение. Глубина проработки зависит от цены ошибки и количества неизвестных.

<HARD-GATE>
Не переходи к реализации, пока существенные решения не сформулированы и не согласованы с пользователем. Не пересматривай уже утверждённые решения, если в спецификации нет пробелов или противоречий.
</HARD-GATE>

## Когда навык не нужен

Не запускай отдельную проработку для:

* точной механической правки без неоднозначности
* исследования, рецензии или диагностики без запроса на изменение
* реализации по полной утверждённой спецификации

В этих случаях сразу используй подходящий навык или выполняй задачу.

## Порядок работы

1. Изучи контекст: файлы, документацию, локальные инструкции и недавние изменения
2. Оцени неизвестные и цену ошибки. Если задача слишком велика, сначала раздели её на независимые части
3. Уточни цель, ограничения и критерии успеха:
   * задавай вопросы по одному, если ответ меняет следующий вопрос
   * собери вопросы в один блок, если пользователь просит их разом или они независимы
   * не переспрашивай то, что уже явно задано
4. Предложи два-три подхода, только если есть содержательно разные варианты. Начни с рекомендации и объясни компромиссы
5. Представь решение соразмерно задаче: коротким абзацем для простой развилки или разделами для сложной системы. Согласуй только открытые и значимые решения
6. После согласования зафиксируй результат по правилам ниже

## Как фиксировать решение

Отдельный документ с решением нужен, если:

* его просит пользователь или требуют локальные инструкции
* решение затрагивает несколько частей системы, его будет дорого изменить или оно понадобится другим участникам

Иначе достаточно согласованного решения в разговоре.

По умолчанию сохраняй документ в `docs/specs/YYYY-MM-DD-{тема}.md`, если проект не задаёт другой путь. Перед передачей проверь документ на незаполненные места, противоречия, неоднозначность и лишний объём.

### Фиксация изменений в Git

| Условие                                                       | Действие                                                     |
| ------------------------------------------------------------- | ------------------------------------------------------------ |
| Пользователь явно просит зафиксировать изменения в Git        | Зафиксируй только документ с решением                        |
| Локальные инструкции требуют фиксации изменений на этом этапе | Выполни их                                                   |
| Ни одно условие не выполнено                                  | Не фиксируй документ в Git                                   |
| Git не используется                                           | Продолжай без Git и не инициализируй его ради этого процесса |

Не включай в эту фиксацию несвязанные изменения.

## Что делать дальше

* Если пользователь просил только решение, передай результат и остановись
* Если нужна реализация и задача требует отдельного плана, используй навык `writing-plans`
* Если реализацию можно безопасно продолжить без отдельного плана, переходи к подходящему навыку после одобрения решения

## Визуальные вопросы

Предлагай браузерный визуальный режим только тогда, когда сравнение макетов или схем заметно упростит решение. Делай это перед первым таким вопросом, а не заранее. После согласия прочитай `visual-companion.md`; после отказа продолжай текстом. Все подписи и вопросы пиши на языке пользователя.

## Типичные ошибки

* превращать мелкую правку в обязательный многошаговый процесс
* повторно согласовывать уже утверждённые решения
* задавать вопросы по одному вопреки прямой просьбе собрать их разом
* создавать документ, фиксировать изменения в Git или составлять план реализации по умолчанию
