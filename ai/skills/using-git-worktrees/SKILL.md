# Выбор Git-рабочей области

## Назначение

Используй минимальную достаточную изоляцию. Один пишущий поток работает на месте; конкурентная запись и реальные риски получают отдельные рабочие области.

Выбор рабочей области и создание изолирующей ветки не разрешают `commit`, `push`, `merge` или Pull Request. Каждое интеграционное действие требует отдельного действующего подтверждения пользователя. Не выполняй промежуточные `commit` или `push` до одобренной контрольной точки.

Возможность будущего Pull Request не требует ветки заранее. При обычной работе создай её после выбора пользователем Pull Request или непосредственно перед технически обязательным одобренным коммитом. Изолирующая ветка создаётся тогда, когда сама изоляция необходима.

## 1. Осмотр

До изменений определи корень, состояние, ветку и тип рабочей области:

```bash
git rev-parse --show-toplevel
git status --short
git branch --show-current
git rev-parse --git-dir
git rev-parse --git-common-dir
git rev-parse --show-superproject-working-tree 2>/dev/null
git worktree list --porcelain
```

Различие `--git-dir` и `--git-common-dir` означает связанный worktree только вне подмодуля. Уже подходящую изолированную область используй повторно; не создавай вложенную.

## 2. Режимы

| Условие | Режим |
|---|---|
| Один пишущий исполнитель, обычная короткая работа | Текущая рабочая область и ветка |
| Последовательные пишущие исполнители | Одна текущая рабочая область |
| Читающие проверяющие одного неизменяемого снимка | Общий снимок без новой ветки |
| Параллельные пишущие исполнители | Отдельная ветка и отдельный worktree каждому |
| Несвязанные пользовательские изменения | Изолированные ветка и worktree |
| Долгая, рискованная работа или прямой запрос | Изолированные ветка и worktree |

Явное указание пользователя работать в текущей рабочей области или в уже созданной области важнее таблицы. Если режим всё ещё неоднозначен, покажи только выбор:

```text
1. Продолжить в текущей рабочей области
2. Создать изолированную рабочую область: <ветка> в <путь>
```

Ветку и путь выведи автоматически из задачи; отдельный вопрос об имени не нужен. Меню выбирает только место работы, а не способ будущей интеграции.

## 3. Создание изоляции

Запиши базовую ветку и исходный `HEAD`. Получи из названия задачи короткий идентификатор в нижнем регистре с дефисами. По умолчанию используй:

```text
ветка: codex/<идентификатор>
путь:  .worktrees/<идентификатор>
```

При коллизии добавь `-2`, `-3` и так далее. Если среда предоставляет штатный инструмент worktree, используй его лишь когда он соблюдает выбранные ветку, путь и правила владения. Иначе:

```bash
git check-ignore -q .worktrees
git worktree add .worktrees/<идентификатор> \
  -b codex/<идентификатор> <базовый_HEAD>
```

Запиши базовую ветку, исходный `HEAD`, созданные ветку и путь в план или отчёт процесса. Отдельно укажи, создал ли текущий процесс ветку и создал ли он worktree: владение одним объектом не означает владение другим. Эти данные определяют будущее меню и допустимую очистку.

Если `.worktrees/` не игнорируется, добавь его в `.gitignore` до создания. Само это изменение не разрешает `commit`. Локальная конвенция проекта имеет приоритет над именами выше.

Если обязательная изоляция недоступна, останови пишущего исполнителя и сообщи препятствие. Не подменяй параллельную изоляцию совместной записью.

## 4. Исходная проверка

В выбранной области зафиксируй исходный `git status` и запусти уместные проверки. Не устанавливай зависимости и не меняй соседние файлы без необходимости. Если исходная проверка неуспешна, отдели прежний сбой от задачи и запроси решение, когда продолжение сделает результат неоднозначным.

## 5. Техническая контрольная точка

Иногда инструмент ревью или передачи результата принимает только Git-коммиты. Это техническая контрольная точка, а не интеграция:

1. Объясни, какой инструмент требует `commit`, и получи отдельное разрешение.
2. Если работа идёт прямо в базовой ветке, создай локальную ветку из текущего состояния непосредственно перед первым `commit`.
3. Фиксируй только файлы задачи; не выполняй `push`.
4. Сохрани базовую ветку и исходный `HEAD` для завершения. Запиши новую ветку как созданную текущим процессом, не меняя прежний признак владения worktree.

Если разрешения нет, используй поддерживаемый неизменяемый снимок без `commit`; если такого способа нет, останови только зависящий от него процесс.

## Сохранение и завершение

Созданные ветка и worktree принадлежат пользователю. Очищай только объекты, созданные текущим процессом, только после выбранного пользователем успешного способа интеграции и при действующем разрешении на конкретную очистку. Завершение работы или название «временный» не разрешает удаление.

## Краткая проверка

| Ошибка | Правило |
|---|---|
| Создать ветку «на случай Pull Request» | Отложить до выбора интеграции |
| Спросить имя worktree | Вывести автоматически из задачи |
| Дать двум исполнителям один каталог | Изолировать каждого либо выполнять последовательно |
| Создать worktree читающему проверяющему | Передать тот же неизменяемый снимок |
| Сделать `commit` сразу после выбора режима | Нужна отдельная контрольная точка и разрешение |
| При ошибке изоляции работать совместно | Остановить запись и сообщить препятствие |
