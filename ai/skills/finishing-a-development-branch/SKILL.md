# Завершение Git-работы

## Назначение

Сначала проверь текущий снимок, затем распознай способ начала работы и покажи
подходящее меню. Любой `commit`, `push`, `merge` или Pull Request выполняется только
после выбора пользователя.

## 1. Проверка результата

Запусти полный уместный набор тестов на состоянии, которое предстоит сохранить
или интегрировать. При неуспехе покажи сбои и не открывай меню интеграции.

Сними состояние до смены каталога:

```bash
git status --short
git branch --show-current
git rev-parse --show-toplevel
git rev-parse --git-dir
git rev-parse --git-common-dir
git worktree list --porcelain
```

Опирайся на записанные ранее базовую ветку, исходный `HEAD`, созданные ветку и
путь и отдельные признаки владения веткой и worktree. Если записи нет,
восстанови происхождение по плану, разговору и истории Git. Не
считай `main` или `master` базовой веткой без подтверждения.

## 2. Выбор меню

| Состояние | Меню | Очистка |
|---|---|---|
| Работа без отдельной ветки, изменения ещё в базовой ветке | Текущее состояние | Нет |
| Именованная рабочая ветка | Интеграция ветки | По результату выбранного действия |
| Отделённый `HEAD` | Создание ветки или сохранение | Оставить среде-владельцу |

Обычная рабочая область сама по себе не означает работу без отдельной ветки: сравни
текущую ветку с записанной базовой.

### Работа без отдельной ветки

Для незакоммиченных изменений покажи:

```text
Работа завершена в текущей ветке <базовая_ветка>. Что сделать?

1. Зафиксировать изменения локально в <базовая_ветка>
2. Зафиксировать и отправить <базовая_ветка> в <удалённый_репозиторий>
3. Создать ветку из текущих изменений, зафиксировать, отправить и создать Pull Request
4. Оставить изменения незакоммиченными
```

Вариант 3 реализует поздний выбор Pull Request: создай автоматически названную
ветку в этой рабочей области, затем фиксируй и отправляй её. Фиктивного слияния
с базовой веткой нет.

Если технические коммиты уже попали прямо в базовую ветку, не переписывай её
автоматически ради Pull Request. Покажи безопасные действия — отправить базовую
ветку или оставить её локально — и отдельно объясни, что перенос в новую ветку
потребует восстановления базовой ветки с явным разрешением.

### Именованная рабочая ветка

```text
Работа завершена в ветке <рабочая_ветка>. Что сделать?

1. Слить локально в <базовая_ветка>
2. Зафиксировать при необходимости, слить локально в <базовая_ветка> и отправить базовую ветку в <удалённый_репозиторий>
3. Отправить <рабочая_ветка> и создать Pull Request
4. Сохранить ветку и рабочую область без изменений
```

В пользовательском тексте подставь настоящее имя базовой ветки. Выбор вариантов
1–3 разрешает только перечисленные действия и необходимую для них фиксацию
файлов задачи.

### Отделённый `HEAD`

```text
Работа завершена в рабочей области с отделённым HEAD.

1. Создать именованную ветку, зафиксировать при необходимости, отправить и создать Pull Request
2. Сохранить текущее состояние без изменений
```

Не предлагай локальное слияние, пока ветка не создана и базовая ветка не
подтверждена.

## 3. Выполнение выбора

### Локальное слияние

До изменения базовой ветки:

1. Зафиксируй только файлы задачи в рабочей ветке, если это нужно, и проверь
   чистое состояние её рабочей области.
2. Если базовая ветка уже открыта в другой рабочей области, используй её только
   при чистом состоянии. Не переключай грязное пользовательское дерево.
3. Если базовая ветка нигде не открыта, чистую текущую область можно переключить
   на неё в рамках выбранного пользователем слияния.
4. Не выполняй `git pull`: вариант должен остаться локальным.
5. Выполни слияние и повтори тесты на результате.

При конфликте или сбое тестов остановись, сохрани ветку и worktree и покажи
фактическое состояние. После успешных тестов очисти только принадлежащую этому
процессу рабочую область.

Для технической ветки, созданной текущим процессом в обычной рабочей области:

1. Зафиксируй разрешённые файлы и убедись, что `git status --short` пуст.
2. Если базовая ветка не открыта в другой области, переключись командой
   `git switch <базовая_ветка>` в этой же чистой области.
3. Выполни `git merge <рабочая_ветка>` и повтори тесты на результате.
4. После успешных тестов удали только созданную процессом рабочую ветку и
   оставь эту рабочую область на базовой ветке: процесс её не создавал.

Если базовая ветка открыта в другой чистой области, сливай там, а исходную
обычную область оставь на рабочей ветке до успешного завершения и затем
переключи обратно только по записанному сценарию. Если безопасный целевой
каталог определить нельзя, остановись и запроси выбор; не создавай временную
область и не переключай постороннюю автоматически.

### Локальное слияние и отправка базовой ветки

До слияния выполни `git fetch <удалённый_репозиторий> <базовая_ветка>` и проверь,
что базовая ветка не отстала и не разошлась с удалённой. При расхождении
остановись до изменения базовой ветки и запроси решение.

Затем локально слей рабочую ветку, повтори тесты и выполни:

```bash
git push <удалённый_репозиторий> <базовая_ветка>
```

Очищай рабочую ветку и worktree только после успешного `push`.

### Pull Request

Зафиксируй файлы задачи, отправь рабочую ветку с настройкой отслеживания и создай
Pull Request против подтверждённой базовой ветки по правилам проекта. Сообщи
ссылку. Сохрани рабочую область для исправления замечаний.

### При отказавшем `push`

Не выполняй `git push --force` и не удаляй данные. Покажи вывод Git и расхождение с
удалённой веткой. Для именованной рабочей ветки сохрани ветку и worktree; после
локального слияния также сохрани локально слитую базовую ветку. Следующее
действие — отдельный выбор пользователя, а не автоматический `pull`, повторное
слияние или откат.

## 4. Очистка

Проверяй владение веткой и worktree независимо. Расположение под `.worktrees/`
не доказывает владение. Ранее существовавшие ветки и worktree сохраняются при
обычном завершении.

Если процесс создал worktree, запускай его удаление снаружи рабочей области и
только при чистом состоянии:

```bash
git worktree remove <путь>
```

Если процесс создал рабочую ветку и она успешно слита, удали только её:

```bash
git branch -d <рабочая_ветка>
```

Не удаляй ветку, если процесс не записал её как созданную им. Не запускай
глобальную очистку записей Git как побочный шаг.

| Выбор | Объект создан процессом | Ранее существовавший объект |
|---|---|---|
| Локальное слияние и зелёные тесты | Удалить принадлежащие ветку и worktree | Сохранить |
| Слияние, успешный `push` и зелёные тесты | Удалить принадлежащие ветку и worktree | Сохранить |
| Pull Request | Сохранить | Сохранить |
| Оставить как есть | Сохранить | Сохранить |
| Любой сбой | Сохранить | Сохранить |

Удаление несмерженной работы не входит в меню. Выполняй его только по прямому
запросу с отдельным перечислением ветки, коммитов и пути и подтверждением слова
`УДАЛИТЬ`.

## Краткая проверка

| Ошибка | Правило |
|---|---|
| Предложить слияние при работе на базовой ветке | Показать меню текущего состояния |
| Сделать `git pull` перед локальным слиянием | Не обращаться к удалённому репозиторию |
| Удалить worktree после создания Pull Request | Сохранить для замечаний |
| Удалить ветку до успешного `push` базовой | Сначала `push`, затем очистка |
| Исправить отказ `push` через `git push --force` | Сохранить состояние и запросить решение |
| Считать любой `.worktrees/*` своим | Проверить запись о владении |
