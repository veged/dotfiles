# Шаблон проверяющего для высокорискового рабочего блока

Используй шаблон только для рабочего блока с риском `high`. Проверяющий
оценивает требования и качество блока; ветка проходит отдельное итоговое
ревью.

```yaml
description: "Проверить рабочий блок N"
fork_turns: "none"
model: "[MODEL — выбрать по риску и сложности]"
message: |
  Проверь высокорисковый рабочий блок N.

  ## Требования

  Файлы задач:

  [BRIEF_FILES]

  Глобальные ограничения:

  [GLOBAL_CONSTRAINTS]

  Отчёт исполнителя: [REPORT_FILE]

  Считай отчёт заявлениями, а не доказательством.

  ## Изменения

  BASE: [BASE_SHA]
  HEAD: [HEAD_SHA]
  Пакет: [DIFF_FILE]

  `HEAD` и пакет образуют неизменяемый снимок. Если фактический `HEAD` или
  проверяемые файлы отличаются, верни `STALE_SNAPSHOT` и не перечитывай
  рабочее дерево.

  Прочитай пакет один раз. В нём есть фиксации Git, общая статистика,
  манифест исключённого содержимого и изменения обычных файлов. Не повторяй
  `git diff` и не обходи репозиторий целиком.

  Проверяй исключённый файл, только если можешь назвать конкретный риск.
  Файл блокировки зависимостей не нужно читать целиком при наличии актуальной
  проверки менеджером пакетов.

  Ничего не меняй в `worktree`, индексе Git, `HEAD` или ветке.

  ## Тесты

  Не повторяй тесты из отчёта для того же `HEAD`. Узкий тест допустим, если
  изменения вызывают конкретное сомнение без ответа в отчёте.

  ## Проверка

  Сопоставь изменения со всеми требованиями:

  - `Missing` — требование не выполнено
  - `Extra` — добавлен лишний объём
  - `Misunderstood` — реализована неверная семантика
  - `Cannot verify` — требование нельзя проверить по пакету

  Затем оцени корректность, обработку ошибок, границы ответственности,
  соответствие проекту и способность тестов поймать дефект.

  Уровни замечаний:

  - `Critical` — потеря данных, уязвимость или системный отказ
  - `Important` — блок нельзя принять без исправления
  - `Minor` — неблокирующее улучшение

  Для каждого замечания укажи `file:line`, риск и исправление, если оно не
  очевидно.

  ## Ответ

  ### Соответствие требованиям
  - Соответствует | Не соответствует
  - Нельзя проверить по пакету: {список}

  ### Сильные стороны
  - {список}

  ### Замечания
  #### Critical
  #### Important
  #### Minor

  ### Вердикт
  Качество блока: Принят | Нужны исправления | Устаревший снимок
  Обоснование: {одно-два технических предложения}

  Начни с раздела «Соответствие требованиям». Не описывай процесс ревью.
```

## Поля шаблона

* `[MODEL]` — выбранная модель
* `[BRIEF_FILES]` — файлы задач рабочего блока
* `[GLOBAL_CONSTRAINTS]` — точные требования спецификации
* `[REPORT_FILE]` — отчёт исполнителя
* `[BASE_SHA]`, `[HEAD_SHA]` — диапазон блока
* `[DIFF_FILE]` — результат `scripts/review-package`
