# Шаблон reviewer для высокорискового Work Unit

Используй только для `high-risk Work Unit`. Reviewer проверяет соответствие
требованиям и качество одного независимо принимаемого блока; широкое ревью
ветки выполняется отдельно.

```yaml
description: "Проверить Work Unit N: требования и качество"
fork_turns: "none"
model: "[MODEL — обязательно выбрать по риску и сложности]"
message: |
  Ты независимо проверяешь high-risk Work Unit N.

  ## Требования

  Прочитай все brief-файлы:

  [BRIEF_FILES]

  Обязательные глобальные ограничения:

  [GLOBAL_CONSTRAINTS]

  ## Заявления implementer

  Прочитай [REPORT_FILE]. Это неподтверждённые заявления, а не доказательство
  корректности.

  ## Изменение

  Base: [BASE_SHA]
  Head: [HEAD_SHA]
  Review package: [DIFF_FILE]

  Прочитай package один раз. Он содержит commits, общую stat, манифест
  исключённого содержимого и diff обычных файлов. Не повторяй git diff и не
  обходи весь репозиторий.

  Если для конкретного риска нужен исключённый файл, назови риск и выполни
  одну сфокусированную проверку. Lock-файл не нужно читать целиком, когда в
  report уже есть актуальная детерминированная проверка package manager.

  Review только для чтения: не меняй worktree, index, HEAD или branch.

  ## Тесты

  Не повторяй набор тестов, уже приведённый implementer для того же Head.
  Запусти только узкий тест, если diff породил конкретное сомнение, на
  которое report не отвечает. Иначе укажи рекомендуемую проверку.

  ## Проверка

  Сначала сопоставь diff со всеми brief:

  - Missing: требование отсутствует;
  - Extra: добавлен ненужный scope;
  - Misunderstood: реализована не та семантика;
  - Cannot verify: требование находится вне видимого diff.

  Затем оцени корректность, обработку ошибок, границы ответственности,
  поддержку существующих паттернов и способность тестов поймать дефект.

  Critical — потеря данных, уязвимость или системный отказ.
  Important — блок нельзя принять без исправления.
  Minor — улучшение, не блокирующее итоговое ревью.

  Каждое замечание должно содержать `file:line`, риск и способ исправления,
  если он не очевиден.

  ## Формат ответа

  ### Соответствие требованиям
  - ✅ Соответствует | ❌ Найдены проблемы
  - ⚠️ Нельзя проверить из diff: [...]

  ### Сильные стороны
  - [...]

  ### Замечания
  #### Critical
  #### Important
  #### Minor

  ### Вердикт
  Work Unit quality: Approved | Needs fixes
  Обоснование: [1–2 технических предложения]

  Начни сразу с раздела `### Соответствие требованиям`; не добавляй рассказ
  о процессе.
```

## Плейсхолдеры

- `[MODEL]` — явно выбранная reviewer-модель.
- `[BRIEF_FILES]` — список brief-файлов всего рабочего блока.
- `[GLOBAL_CONSTRAINTS]` — точные значения и связи из спецификации.
- `[REPORT_FILE]` — отчёт implementer по блоку.
- `[BASE_SHA]`, `[HEAD_SHA]` — полный диапазон блока.
- `[DIFF_FILE]` — путь, выведенный `scripts/review-package`.
