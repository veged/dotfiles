# Шаблон implementer для Work Unit

Используй шаблон для одного независимо принимаемого рабочего блока. Несколько
Task внутри блока передаются отдельными brief-файлами.

```yaml
description: "Реализовать Work Unit N: [название]"
fork_turns: "none"
model: "[MODEL — обязательно выбрать по SKILL.md]"
message: |
  Ты реализуешь Work Unit N: [название].

  ## Требования

  Сначала прочитай все brief-файлы:

  [BRIEF_FILES]

  Вместе они образуют требования одного рабочего блока. Не читай полный
  план и историю сессии.

  ## Контекст

  [Одна строка о месте блока в проекте]

  Нужные интерфейсы и решения предыдущих блоков:
  [INTERFACES]

  Рабочая директория: [WORKDIR]

  ## До начала

  Если требования, зависимости или критерии приёмки неоднозначны, верни
  NEEDS_CONTEXT и задай конкретный вопрос. Не угадывай архитектурные решения.

  ## Работа

  1. Реализуй только требования brief-файлов.
  2. Следуй TDD, если он требуется планом или навыком задачи.
  3. Во время итераций запускай сфокусированные тесты; полный набор — один
     раз перед commit.
  4. Закоммить результат.
  5. Самостоятельно проверь полноту, качество, YAGNI и реальную ценность
     тестов.

  Не рефактори соседний код без необходимости. Если блок оказался
  архитектурно шире brief, остановись с BLOCKED или DONE_WITH_CONCERNS.

  ## Исправления после review

  Если контроллер продолжит тебя с замечаниями, исправь их одной волной,
  повтори только покрывающие тесты и допиши в тот же report:

  - что изменено;
  - какие тесты покрывают исправление;
  - точную команду;
  - существенный результат команды.

  ## Отчёт

  Запиши полный отчёт в [REPORT_FILE]:

  - реализованные требования по каждому brief;
  - commits и изменённые файлы;
  - команды тестов и результаты;
  - RED/GREEN-доказательство, если требовался TDD;
  - результат self-review;
  - concerns или blocker.

  В финальном сообщении верни не более 15 строк:

  - Status: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
  - commits;
  - одну строку о тестах;
  - concerns;
  - путь к report.

  При BLOCKED или NEEDS_CONTEXT продублируй конкретную причину в финальном
  сообщении, чтобы контроллер мог действовать без чтения лишних файлов.
```

## Плейсхолдеры

- `[MODEL]` — явно выбранная модель.
- `[BRIEF_FILES]` — список путей, по одному brief на каждую Task блока.
- `[INTERFACES]` — только необходимые решения и интерфейсы предыдущих блоков.
- `[WORKDIR]` — абсолютный путь к изолированному worktree.
- `[REPORT_FILE]` — один файл отчёта на весь `Work Unit`.
