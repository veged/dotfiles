# Опциональная разработка по OpenSpec

## Цель

Добавить в набор навыков опциональный макропроцесс разработки по OpenSpec.
OpenSpec хранит мотивацию, требования, проект решения и рабочие пункты, а
существующий адаптивный SDD выбирает способ исполнения и управляет агентами.

Текущий процесс остаётся основным. Наличие каталога `openspec/` само по себе
не включает новый навык.

## Активация

Навык `openspec-development` срабатывает, когда:

* пользователь явно просит применить OpenSpec
* пользователь просит продолжить, реализовать или проверить указанное активное
  изменение OpenSpec

Навык не срабатывает только из-за сложности задачи или наличия других активных
изменений. Если OpenSpec не настроен или CLI недоступен, навык не устанавливает
зависимости и не инициализирует проект без отдельного разрешения.

Оркестратор использует только уже установленный CLI из `PATH` или зависимостей
проекта. Он не разрешает `npx` скачивать пакет во время проверки доступности.

При нескольких активных изменениях пользователь выбирает одно. При отсутствии
активного изменения явный запрос на OpenSpec создаёт новое изменение через
штатный CLI.

## Архитектура

Процесс состоит из двух независимых уровней:

1. `openspec-development` управляет артефактами и переходами между
   планированием, утверждением, исполнением и ревью
2. `subagent-driven-development` группирует рабочие пункты, выбирает агентов и
   проводит проверки реализации

Детерминированные решения `openspec-development` выполняет один исполняемый
интерфейс `openspec-orchestrate`. Он принимает локальный снимок события,
`state.md` и явно выбранный CLI OpenSpec, затем возвращает JSON с действиями и
атомарно обновляет известные поля состояния. Интерфейс не запускает агентов:
навык исполняет наблюдаемые действия через сохранённые ID ролей.

```text
Обычная задача
    → brainstorming
    → writing-plans
    → executing-plans или subagent-driven-development

Явная задача OpenSpec
    → openspec-development
        → planner
        → утверждение плана
        → один исполнитель или subagent-driven-development
        → одно итоговое ревью
        → свежая проверка
        → готово к слиянию

После слияния и только по явному запросу
    → openspec-archive
```

OpenSpec не копирует правила рабочих блоков, бюджетирования, моделей и пакетов
ревью. SDD не знает о графе артефактов и командах OpenSpec.

## Источники истины

Источники истины расположены в следующем порядке:

1. Артефакты OpenSpec и ответы CLI определяют принятые требования и состояние
   рабочих пунктов
2. Git определяет фактическую реализацию и проверяемый `HEAD`
3. Отчёты агентов содержат доказательства исполнения и проверки
4. Оперативный журнал помогает восстановить сессию, но не переопределяет
   OpenSpec или Git

`openspec-orchestrate` служит исполняемым источником истины для ветвей и
переходов. Входной снимок не становится новым хранилищем требований: он только
проецирует факты OpenSpec, Git и отчётов в решение процесса.

Подробности из чата, которые влияют на результат, должны попасть в артефакт,
отчёт или журнал. Незафиксированная переписка не считается долговременным
состоянием.

## Состояние процесса

Для каждого изменения создаётся рабочая область:

```text
.superpowers/openspec/{change-name}/
```

Каталог скрыт от Git. Файл `state.md` содержит:

* имя изменения и текущий этап
* ID `planner`, исполнителя и `reviewer`
* режим исполнения `single` или `sdd`
* путь к рабочей области SDD
* последний проверенный `HEAD`
* открытые замечания и их категории
* пути к отчётам агентов

Этапы:

```text
discover
    → planning
    → human-approval
    → execution
    → review
    → fresh-verification
    → ready-for-merge
```

Архивация не входит в эту машину состояний.

В новом чате оркестратор восстанавливает этап по `openspec list --json`,
`openspec status --json`, `openspec instructions apply --json`, Git и
`state.md`. Отсутствие прежнего ID агента не блокирует продолжение. Новый агент
получает артефакты, последний отчёт и открытые замечания без истории чата.

Если журнал расходится с OpenSpec или Git, оркестратор исправляет журнал по
источникам истины и записывает причину.

Навык не меняет известные поля журнала вручную. Для событий `discover`,
`recover`, `route`, `review`, `review-complete`, `findings`, `verify`,
`archive-guard` и `archive-impact` он вызывает `openspec-orchestrate`.

## Контракт контекста

Каждый агент получает `fork_turns: "none"` и выбранную по роли и риску модель.
Имена моделей не закрепляются в навыке.

Агент пишет подробности в файл, а в ответ возвращает не более 15 строк:

* статус
* категории замечаний или препятствия
* проверенный `HEAD`
* путь к отчёту

Повторный вызов продолжает того же агента и передаёт только новое сообщение,
отчёт или пакет исправлений. Оркестратор передаёт компактный ответ дословно, а
полные требования и замечания — путями к файлам.

При замене агента оркестратор записывает причину и пересчитывает бюджет. Новый
агент восстанавливается из файлов, а не из пересказа истории.

## Планирование

`planner` исследует код и работает только с артефактами активного изменения. Для
каждого артефакта он получает свежие инструкции CLI, читает зависимости,
записывает результат по указанному пути и повторно проверяет состояние.

`planner` завершает этап только тогда, когда:

* все артефакты, необходимые для применения, готовы
* `openspec validate` завершается успешно
* отсутствуют решения, которые должен принять пользователь

Оркестратор показывает ссылки на конкретные артефакты и запрашивает разрешение
на реализацию. Замечание пользователя возвращается тому же `planner`.

Если позднее изменение артефакта делает выполненный рабочий пункт устаревшим,
`planner` снимает отметку только с затронутого пункта.

## Выбор исполнения

После утверждения оркестратор получает `openspec instructions apply --json` и
передаёт контекст политике исполнения.

Рабочие пункты группируются по определению рабочего блока из SDD:

* один связный блок выполняет один постоянный исполнитель
* минимум два независимо принимаемых блока выполняет адаптивный SDD

Для OpenSpec создаются готовые файлы кратких заданий. SDD принимает их от
вызывающего навыка и не разбирает формат OpenSpec самостоятельно.

Рабочая область SDD должна зависеть от полного относительного пути плана, а не
только от имени `tasks.md`. Это предотвращает столкновение одноимённых планов
разных изменений OpenSpec.

Исполнитель:

* читает контекст применения и относящееся к рабочему блоку краткое задание
* следует утверждённым артефактам и не меняет их самостоятельно
* запускает проверки изменённого кода
* отмечает только фактически выполненные рабочие пункты
* записывает отчёт с командами, результатами и проверенным `HEAD`

## Ревью

В процессе выполняется ровно одно итоговое ревью всей реализации:

* в режиме `single` его проводит отдельный проверяющий OpenSpec
* в режиме `sdd` итоговый `reviewer` SDD одновременно проверяет реализацию по
  OpenSpec

После SDD не запускается вторая полная проверка. Проверяющий получает
контекст OpenSpec, отчёты исполнения и ограниченный пакет изменений.

`reviewer` ничего не меняет и возвращает замечания категорий:

* `artifact {id}` — ошибка или пробел в артефакте
* `implementation` — несоответствие реализации утверждённым артефактам
* `external` — отсутствующие данные, доступ или решение пользователя

Уровни `Critical` и `Important` блокируют завершение. `Minor` сохраняются в
журнале с решением.

После чистого ревью оркестратор сам запускает свежие проектные проверки,
доказывающие итоговое состояние. Отчёт исполнителя или `reviewer` не заменяет
эту проверку.

## Смешанные замечания

Если `reviewer` одновременно нашёл ошибки артефактов и реализации:

1. все замечания записываются в файл
2. `planner` исправляет артефакты и снимает устаревшие отметки
3. исполнитель получает обновлённые артефакты и прежние замечания к коду одним
   пакетом
4. неактуальные замечания помечаются `OBSOLETE`, остальные исправляются
5. тот же `reviewer` проверяет пакет исправлений

Замечания к реализации не ждут нового полного ревью, чтобы быть обнаруженными
повторно. При потере ID `reviewer` новый проверяющий получает файл замечаний и
пакет исправлений.

## Обратная связь во время работы

Изменение требований или проекта решения возвращает процесс в `planning`.
Текущее ревью и его пакет становятся устаревшими.

Исправление кода, не меняющее утверждённые артефакты, возвращает процесс в
`execution`. Повторно используется исполнитель соответствующего блока.

Внешний блокер задаётся пользователю одним конкретным вопросом. Ответ
возвращается тому же агенту.

Субъективные артефакты сохраняют правило SDD: дешёвая проверка, показ
пользователю, явное подтверждение, затем дорогая проверка и итоговое ревью.

## Архивация

Отдельный навык `openspec-archive` запускается только по явному запросу после
слияния.

Он:

1. определяет основную ветку проекта, не предполагая `main` или `master`
2. требует чистую рабочую копию в основной ветке
3. проверяет завершённость артефактов и рабочих пунктов
4. запускает штатный `openspec archive`
5. не переключает ветки, не сливает изменения и не создаёт коммит

Ошибка формы артефакта возвращается `planner` и допускает повтор архивации. Если
исправление меняет требования, решение или реализацию, архивирование
останавливается и начинается новый цикл разработки.

## Изменения SDD

SDD получает только общие расширения:

* готовые файлы кратких заданий от вызывающего навыка
* устойчивый идентификатор рабочей области по пути плана
* шаблон одного итогового `reviewer` с дополнительными файлами требований
* правило, запрещающее вызывающему навыку запускать второе полное ревью

В SDD не добавляются команды OpenSpec, его категории артефактов или логика
архивации.

## Проверка

Автоматический сценарный тест вызывает `openspec-orchestrate`, подменённый CLI
OpenSpec и реальные вспомогательные скрипты с локальными данными JSON. Он
проверяет команды, решения и изменения `state.md`, а не наличие фраз в
документации. Сеть и установленный OpenSpec для него не нужны.

Обязательные сценарии:

1. обычная задача не включает OpenSpec
2. явный запрос создаёт или продолжает выбранное изменение
3. несколько активных изменений требуют выбора
4. новый чат восстанавливает этап без ID агента
5. одноимённые `tasks.md` получают разные рабочие области
6. один рабочий блок выбирает одного исполнителя
7. несколько независимых рабочих блоков выбирают SDD
8. SDD принимает готовые файлы кратких заданий
9. после SDD выполняется одно, а не два итоговых ревью
10. смешанные замечания проходят `planner`, исполнителя и одну повторную проверку
11. устаревшие рабочие пункты снова становятся незавершёнными
12. свежая проверка относится к текущему `HEAD`
13. архивирование блокируется вне чистой основной ветки
14. влияние исправления архива на код возвращает изменение в разработку

Дополнительно запускаются существующие тесты SDD, установки и слоёв навыков,
проверка Markdown и синтаксиса скриптов.

## Ошибки и ограничения

* Недоступный CLI OpenSpec — внешний блокер, а не повод установить зависимость
* Невалидный артефакт возвращается `planner`
* Неполные рабочие пункты не позволяют перейти к ревью
* Несовпадение проверенного `HEAD` делает отчёт устаревшим
* Переполнение пакета ревью обрабатывается существующими правилами SDD
* Потеря ID агента увеличивает бюджет, но не требует повторять завершённые этапы
* Изменение артефактов после реализации требует повторно выполнить только
  затронутые пункты

## Критерии готовности

Решение готово, если:

* OpenSpec включается только явно или для указанного активного изменения
* обычный процесс и существующие тесты SDD не меняют поведение
* артефакты OpenSpec остаются единственным источником требований
* исполнение адаптируется к связанности и риску рабочих блоков
* каждый новый агент и дополнительное ревью учитываются в бюджете
* после SDD проводится ровно одно итоговое ревью
* процесс восстанавливается без истории чата
* завершение подтверждается свежими проверками текущего `HEAD`
* архивирование выполняется отдельно после слияния
* все 14 сценариев проходят через исполняемый интерфейс переходов
